3. 발견한 기술적 문제와 해결 방법
--------------------------------------------------------------------

[문제 1] 이 프로젝트의 LeRobotDataset은 codebase_version "v3.0"을 강제함
  (check_version_compatibility, major version 2 < 3 이면 즉시 에러).
  즉 human(v2.1)도 mg(v2.0)도 변환 없이는 로드 불가.

[문제 2] 이 저장소에 이미 있는 변환 스크립트
  src/lerobot/scripts/../datasets/v30/convert_dataset_v21_to_v30.py 는
  이름 그대로 "v2.1 -> v3.0" 전용이며, v2.0 입력은 명시적으로 거부함
  (validate_local_dataset_version, meta/episodes_stats.jsonl 를 필수로 읽음).
  즉 mg(v2.0)를 곧바로 이 스크립트에 넣을 수 없음.

  -> upstream lerobot에는 예전에 v2.0->v2.1 변환 스크립트
     (lerobot/datasets/v21/convert_dataset_v20_to_v21.py)가 있었으나,
     v3.0 도입 커밋(1f70938 "Dataset v3 (#1412)")에서 통째로 삭제됨.
     git 히스토리에서 옛 버전을 확인했지만 그 스크립트는 HF Hub 업로드를
     전제로 동작해서 로컬 전용 파이프라인에는 그대로 못 씀.

  -> 해결: tools/convert_v20_to_v21_local.py 를 새로 작성.
     LeRobotDataset을 거치지 않고 raw parquet/mp4 파일을 직접 읽어
     (lerobot.datasets.compute_stats.get_feature_stats,
      lerobot.datasets.video_utils.decode_video_frames 활용) 에피소드별
     통계를 계산하고 meta/episodes_stats.jsonl 을 생성, codebase_version을
     "v2.1"로 올림. 비디오 통계는 프레임을 성기게(기본 8프레임) 샘플링하는데,
     이는 이 프로젝트가 기본값으로 dataset.use_imagenet_stats=true 를 쓰기
     때문에(factory.py: make_dataset 이 카메라 키 통계를 ImageNet 고정값으로
     덮어씀) 학습 정규화에는 실제로 쓰이지 않아 정밀도가 중요하지 않음을
     확인하고 내린 결정.

[문제 3] mg의 원본 info.json에 observation.state/action의 dtype이 "object"로
  잘못 기재되어 있음 (실제 parquet 상 물리 타입은 list<double>). "object"는
  유효한 arrow/HF dtype이 아니라서 LeRobotDataset 로드 자체가 즉시 실패함.
  -> RoboCasa mg 익스포트 파이프라인의 메타데이터 버그로 판단, 두 필드의
     dtype 문자열만 "float64"로 고쳐서 해결 (실 데이터는 그대로).

[문제 4] 이 프로젝트의 멀티 데이터셋 학습 경로
  (--dataset.repo_id=[a,b] 형태, lerobot/datasets/factory.py::make_dataset)는
  per-dataset episode 서브셋 지정을 지원하는 것처럼 보이지만 실제로는
  episodes_dict = {} 로 항상 빈 채로 MultiLeRobotDataset에 넘겨서 무조건
  전체 에피소드를 다 불러옴. 즉 "mg에서 N개만" 같은 제한을 CLI로 걸 수 없음.
  -> 해결: 학습 전에 아예 물리적으로 "human 전체 + mg 일부"를 합친 단일
     v3.0 데이터셋을 미리 만들어서, 학습 스크립트는 평범한 단일
     --dataset.repo_id 로 그 결과물만 가리키게 함.

[문제 5] human과 mg의 feature 스키마가 완전히 같지 않아서
  (aggregate_datasets가 요구하는) 정확히 동일한 meta.features 비교를
  통과하지 못함:
    - mg에는 frame_index 컬럼이 아예 없음 (human에는 있음)
    - next.reward dtype이 다름 (human: float32, mg: float64)
    - timestamp/episode_index/index/task_index 등에 human쪽만 있는
      부가 "fps" 키, video 쪽 "info" 서브딕셔너리 유무 차이 (전부
      데이터 자체와 무관한 서술 메타데이터 차이)
  -> 조사 중 추가로 확인한 사실: LeRobotDatasetMetadata.create() 는
     {**features, **DEFAULT_FEATURES} 로 timestamp/frame_index/
     episode_index/index/task_index 5개 컬럼을 항상 "정규(canonical)"
     형태로 덮어씀. 즉 split_dataset/add_features를 한 번이라도 거치면
     이 5개 필드는 항상 그 축소된 형태로 수렴함. 그래서 mg에 frame_index가
     없는 채로 split_dataset을 돌리면, 메타데이터는 frame_index가 있다고
     선언하는데 실제 parquet에는 없는 상태가 되어 즉시 에러가 남
     (datasets 라이브러리의 "Keys mismatch: source/target" 에러로 재현 확인).
  -> 해결: tools/prepare_robocasa_dataset.py 안에
     normalize_default_features() 로 두 데이터셋 모두 5개 표준 컬럼을
     DEFAULT_FEATURES 정의값으로 먼저 통일하고, harmonize_mg_to_human()
     에서 mg에 frame_index(=arange(episode_length), 진짜 올바른 값)를
     추가하고 next.reward를 float32로 캐스팅.

[문제 6] (가장 까다로웠던 버그) 위 하모나이즈 작업을 add_features/
  remove_feature 를 여러 번 나눠서 호출했더니, 그 이후 merge된 최종
  데이터셋에서 mg 쪽 에피소드의 비디오 프레임이 일부(첫/중간/끝 프레임)
  디코드가 안 되는 문제 발생 (pyav: "avcodec_send_packet ... no frame!").
  캐시 오염(HF datasets 캐시가 repo_id만으로 키잉되어 이전 테스트의 다른
  경로 데이터를 잘못 재사용하는 문제)까지 겹쳐서 원인 파악이 오래 걸림.
  HF_DATASETS_CACHE를 매번 비우고 고유 repo_id로 재현한 결과:
    - harmonize 단계 산출물(mg_harmonized) 단독: 정상 디코드
    - split_dataset 산출물(mg_subset) 단독: 정상 디코드
    - merge_datasets로 human + mg_subset을 합친 최종 결과물: 깨짐
  -> lerobot/datasets/aggregate.py::aggregate_videos 가, 서로 다른
     소스 데이터셋의 이미 완성된 비디오 청크 파일을
     concatenate_video_files() 로 이어붙이는 과정에서 문제가 생기는
     것으로 결론 (같은 데이터셋 내부에서의 이어붙이기는 문제 없음 -
     human 자체 변환 결과는 정상이었음). 이는 이 프로젝트의 기존
     dataset_tools/aggregate 코드에 있던 버그로 보이며, 내가 새로
     만든 코드 때문에 생긴 문제가 아님.
  -> 해결: dataset_tools.merge_datasets() 대신
     lerobot.datasets.aggregate.aggregate_datasets() 를 직접 호출하면서
     video_files_size_in_mb 를 아주 작은 값(0.001)으로 강제. 그러면
     소스별로 항상 "새 파일 시작"(단순 파일 복사) 분기만 타서
     concatenate_video_files 자체가 호출되지 않음 (출력 비디오 파일 수는
     늘지만 학습에는 지장 없음). 실제 6개 에피소드(human 4 + mg 2)짜리
     축소 테스트로 전체 프레임 샘플(첫/중간/끝) 및 DataLoader 배치 추출까지
     정상 동작 확인.

  참고: harmonize 단계도 처음엔 add_features/remove_feature를 여러 번
  나눠 호출했는데, 그때마다 dataset_tools._copy_videos가 비디오를
  다시 인코딩(SVT-AV1)하는 것을 확인. 재인코딩 자체가 문제를 일으키는지는
  끝까지 명확히 특정하지 못했고(최종 원인은 위의 cross-dataset concat으로
  좁혀짐), 다만 재인코딩 횟수를 줄이는 게 안전하다고 보고 harmonize 단계를
  단일 modify_features 호출로 합쳐서 재인코딩 횟수를 최소화해 둠.

4. 만든 파일
--------------------------------------------------------------------

  tools/convert_v20_to_v21_local.py
    - RoboCasa mg처럼 codebase_version "v2.0"인 로컬 데이터셋을
      "v2.1"로 변환(에피소드별 통계 생성 + stats.json 제거 + 버전 갱신).
      이미 v2.1 이상이면 아무 것도 안 하고 스킵(재실행 안전).

  tools/prepare_robocasa_dataset.py
    - 전체 준비 파이프라인의 오케스트레이터. 실행 흐름:
        1) --source-human / --source-mg 를
           dataset_git/robocasa_turnonsinkfaucet/raw/{human,mg} 로 복사
           (원본 데이터는 절대 건드리지 않음)
        2) mg가 v2.0이면 convert_v20_to_v21_local 적용
        3) 기존 convert_dataset_v21_to_v30.py 로 둘 다 v3.0 변환
        4) normalize_default_features + harmonize_mg_to_human 으로
           스키마 통일
        5) mg를 앞에서부터 필요한 개수(= total-episodes - human 개수)만큼
           split_dataset 으로 잘라서 mg_subset 생성 (결정적, 인덱스 순서)
        6) aggregate_datasets 로 human 전체 + mg_subset 을 최종 병합
           -> <output-root>/merged
     각 단계는 결과물이 이미 있으면 건너뛰어서(idempotent) 중간에 실패해도
     재실행 시 이어서 진행됨. --force로 강제 재실행 가능.

  train_smolVLA_robocasa.sh
    - train_smolVLA_scaling.sh 구조를 따름 (accelerate multi-GPU launch,
      동일한 policy/훈련 하이퍼파라미터 스타일).
    - 학습 전에 위 prepare_robocasa_dataset.py 를 먼저 호출해서 병합
      데이터셋이 존재/최신 상태인지 보장.
    - 기본값:
        TOTAL_EPISODES=3000
        SOURCE_HUMAN=.../TurnOnSinkFaucet/20250819/lerobot
        SOURCE_MG=.../TurnOnSinkFaucet/20250819/mg/demo/2025-08-21-12-24-03/lerobot
        DATASET_ROOT=dataset_git/robocasa_turnonsinkfaucet
        USE_WRIST_CAM=true (이 데이터는 실제 wrist cam(robot0_eye_in_hand)이
          있어서, LIBERO용 스크립트들과 달리 기본을 true로 설정)
        POLICY_VISUAL_CUE_MODE=vanilla (scaling.sh는 plucker_concat을
          쓰지만, 이 데이터셋에 대해 plucker에 필요한 카메라 intrinsics
          제공 여부를 확인하지 못해 안전하게 vanilla를 기본값으로 설정.
          필요시 env var로 plucker_concat 지정 가능)
     모든 값은 환경변수로 오버라이드 가능 (스크립트 상단 주석 참고).

5. 검증 (실제로 수행한 것)
--------------------------------------------------------------------
- 실제 TurnOnSinkFaucet human/mg 원본에서 각각 3~4개 에피소드만 잘라낸
  축소 사본으로 prepare_robocasa_dataset.py 전체 파이프라인을 처음부터
  끝까지 여러 차례 실행하며 디버깅 (raw copy -> v2.0->v2.1 shim ->
  v2.1->v3.0 변환 -> harmonize -> split -> merge).
- 최종 병합 데이터셋(6 에피소드 = human 4 + mg 2)에 대해:
    - 모든 에피소드의 첫/중간/끝 프레임 디코드 성공 확인 (pyav backend)
    - PyTorch DataLoader로 실제 배치(batch_size=8) 추출 성공,
      action/state/image 텐서 shape 정상 확인
    - 스크립트 재실행 시 idempotent하게 스킵되는 것도 확인
- 이 저장소 실행 환경에는 torchcodec이 설치돼 있지만 시스템 FFmpeg 공유
  라이브러리가 없어 로드 실패함을 확인(libavutil.so.* 없음). 실제 학습
  머신에서는 정상일 수 있어 학습 스크립트 자체는 기존 스크립트들과 동일하게
  video_backend를 강제하지 않았음. 데이터 준비 스크립트(내부적으로 비디오를
  디코드해서 통계를 내는 부분)만 안전하게 backend="pyav"를 기본값으로 씀.

6. 아직 안 한 것 / 사용자가 직접 해야 할 것
--------------------------------------------------------------------
- 실제 전체 규모(human 107 + mg 2893 = 3000 에피소드) 데이터 준비는
  아직 실행하지 않음. mg 원본이 9524 에피소드(4.7GB)라서:
    - v2.0->v2.1 통계 계산 + v3.0 변환 + harmonize(비디오 재복사 포함)
      단계가 상당히 오래 걸릴 수 있음(정확한 시간 미측정, GPU 학습과
      무관하게 CPU/디스크 I/O 바운드 작업). 원격에서 자원을 오래 점유하는
      작업이라 사용자 확인 없이 자동으로 돌리지 않았음.
  -> 실행 방법: 그냥 ./train_smolVLA_robocasa.sh 를 실행하면 됨.
     처음 실행 시 데이터 준비가 자동으로 먼저 돌고, 완료되면 이어서
     학습이 시작됨. 준비만 먼저 따로 오래 돌리고 싶다면:
       python tools/prepare_robocasa_dataset.py \
         --source-human "<human 경로>" \
         --source-mg "<mg 경로>" \
         --output-root dataset_git/robocasa_turnonsinkfaucet \
         --total-episodes 3000
- mg에서 뽑는 2893개 에피소드 선정 방식은 "인덱스 순서로 앞에서부터
  결정적으로 N개"로 정함 (무작위 샘플링이 아님). 요청에는 방식이
  명시되지 않아 내가 내린 선택이며, 무작위 샘플링을 원하면 말씀해주시면
  프로세스를 바꿀 수 있음.
- POLICY_VISUAL_CUE_MODE 기본값(vanilla)과 USE_WRIST_CAM(true)은 내
  판단으로 정한 기본값. 다른 학습 스크립트들과 다른 세팅을 원하면
  실행 시 환경변수로 덮어쓰면 됨.

7. 2차 피드백 및 재설계 (같은 날 후속 요청)

--------------------------------------------------------------------
7.1 사용자 피드백 (원문 요지)
--------------------------------------------------------------------
"convert_v21_to_v30_multiple.sh 이런걸 만들어서 데이터셋을 전부 v30으로
맞춰놓고 그 데이터셋을 가져와서 돌리면 될 것 같아. 그리고 cam은
robot0_agentview_right과 robot0_eye_in_hand 를 써서 학습하면 돼"

즉 1차 버전(별도의 merge된 단일 데이터셋을 만드는 방식)이 과했다는 피드백.
convert_v21_to_v30_multiple.sh 처럼 "그냥 v3.0으로 변환해두고, 기존
train_smolVLA_scaling.sh류 스크립트들이 쓰는 방식(--dataset.repo_id=[a,b]
리스트 문법)으로 바로 돌리면 된다"는 훨씬 단순한 방향 요청. 추가로 카메라는
robot0_agentview_right + robot0_eye_in_hand 두 개만 쓰고
robot0_agentview_left는 빼라는 요청.

--------------------------------------------------------------------
7.2 재설계하면서 새로 확인한 사실들
--------------------------------------------------------------------
- 이 프로젝트의 --dataset.repo_id=[a,b] (MultiLeRobotDataset) 경로는
  1차 조사에서 발견한 "per-dataset episode 제한 불가" 문제는 여전히
  있지만(episodes_dict가 항상 빈 채로 넘어감), MultiLeRobotDataset 자체는
  merge_datasets/aggregate_datasets와 달리 두 데이터셋의 feature 스키마가
  완전히 같을 것을 요구하지 않음 - 공통 키만 남기고 나머지는 그냥
  "disabled_features"로 취급해 경고만 찍고 넘어감. 즉 1차 버전에서 했던
  frame_index 추가, "fps" 부가 키 통일 같은 하모나이즈 작업이 전혀
  필요 없어짐.
- 대신 "에피소드 개수 제한"은 (episodes_dict 버그 때문에) CLI로 못 거니까,
  변환 *이전* 단계에서 mg 원본 파일을 필요한 개수만큼만 물리적으로 잘라서
  복사하는 방식으로 처리하기로 함 (split_dataset을 아예 안 씀). 이렇게
  하면 1차 버전에서 발견했던 두 가지 버그를 모두 안 만나게 됨:
    (a) split_dataset이 LeRobotDatasetMetadata.create()의
        {**features, **DEFAULT_FEATURES} 때문에 frame_index를 없는 채로
        선언해버리는 버그
    (b) aggregate_datasets(merge_datasets)가 서로 다른 소스의 비디오
        청크를 이어붙일 때 프레임을 깨뜨리는 버그
  -> 애초에 merge/split을 쓰지 않으므로 두 버그 다 회피됨. 데이터 준비도
     mg 9524개 전체가 아니라 필요한 개수(예: 2893개)만 처리하므로 훨씬
     빠름 (특히 가장 비싼 v2.0->v2.1 통계 계산 단계).
- 카메라 필터링(robot0_agentview_left 제거)은 dataset_tools.remove_feature
  를 쓸 수도 있었지만, 그러면 전체 데이터를 다시 복사하고 비디오도 다시
  손대야 해서(1차에서 겪은 재인코딩 이슈 재발 위험) 대신 애초에 raw 파일을
  dataset_git으로 복사하는 단계에서 robot0_agentview_left 비디오 파일
  자체를 복사하지 않고 info.json/episodes*.jsonl 에서 해당 feature만
  지우는 방식으로 처리 (훨씬 싸고 안전함).
- 카메라를 걷어내는 김에 human vs mg의 실제 dtype 불일치를 원본에서 다시
  전수 비교함:
    action/observation.state: human=float64, mg="object"(버그, 실제
      데이터는 float64) -> 라벨만 수정
    timestamp/next.reward: human=float32, mg=float64 (실제 데이터가
      다름) -> 그냥 라벨만 고치면 안 되고 parquet 컬럼 자체를 float32로
      캐스팅해야 함. 이유: MultiLeRobotDataset은 human/mg 두 데이터셋의
      아이템을 같은 배치에 섞어서 반환하는데, PyTorch 기본 collate가
      torch.stack을 쓰면서 같은 키(next.reward 등)에 대해 배치 내
      dtype이 섞이면(float32 vs float64) 즉시 에러가 남. 실제로 이
      캐스팅을 빼고 테스트했으면 학습 시작하자마자 크래시났을 것.
- 추가로 발견한 별개의 기존 버그: MultiLeRobotDataset.__init__ 이
  `dataset.meta.stats.pop('observation.environment_state')` 를 인자 없이
  호출해서, environment_state 피처가 없는 데이터셋(RoboCasa 포함, LIBERO
  전용 가정인듯)에서는 KeyError로 즉시 죽음. src/lerobot/datasets/
  lerobot_dataset.py 에서 `.pop('observation.environment_state', None)`
  으로 한 줄 수정해서 해결 (기존 LIBERO 동작에는 영향 없음 - 그 경우엔
  키가 원래 있으니 pop이 그대로 성공).

8.1 1단계: 데이터 준비 (tools/prepare_robocasa_dataset.py 호출)

소스:
  SOURCE_HUMAN = .../TurnOnSinkFaucet/20250819/lerobot
  SOURCE_MG    = .../TurnOnSinkFaucet/20250819/mg/demo/2025-08-21-12-24-03/lerobot
  TOTAL_EPISODES = 3000 (기본값)

실제 소스 데이터 크기(2026-07-28 재확인):
  - human: codebase_version=v3.0(이미 변환된 상태로 다시 확인됨),
    total_episodes=107, total_frames=23,795, fps=20

    total_frames=2,292,897, fps=20

가져오는 양 (episode_index 앞에서부터 결정적으로 자름):
  - human: 107개 전부 (100%) -> 23,795 프레임
  - mg: 3000 - 107 = 2,893개만 사용 (소스 9,524개 중 앞쪽 2,893개,

    첫 2,893개 에피소드 length 합)
  - 합계: 107 + 2,893 = 3,000 episodes, 23,795 + 694,992 = 718,787 frames
    (약 20fps 기준 약 10시간 분량)
  - 카메라는 두 데이터셋 모두 agentview_right + eye_in_hand 2대만 남김

이 준비 단계는 idempotent: dataset_git/robocasa_turnonsinkfaucet/raw/
{human,mg} 가 이미 있으면 통째로 스킵 (--force 로 강제 재실행 가능).
아직 이 디렉토리는 생성된 적 없음(2026-07-28 기준 NOT YET CREATED) ->
처음 실행하면 전체 파이프라인(카메라 필터링 복사 -> mg dtype 버그 수정
-> mg v2.0->v2.1 통계 계산 -> 둘 다 v2.1->v3.0 변환)이 처음부터 돈다.
mg 2,893개에 대한 v2.0->v2.1 per-episode 통계 계산이 가장 오래 걸리는
단계.

8.2 2단계: 학습 (accelerate launch ... lerobot_train.py)
--------------------------------------------------------------------
- --dataset.repo_id="[human,mg]" + --dataset.root=raw 디렉토리 로
  MultiLeRobotDataset 이 두 데이터셋을 하나의 학습 스트림으로 합침

- policy: smolvla, visual_cue_mode=vanilla (plucker 아님 - 이 데이터셋은
  카메라 intrinsics 준비가 확인 안 돼서 안전한 기본값 사용),
  load_vlm_weights=true, freeze_vision_encoder=false, train_expert_only=false
  -> VLM 백본까지 포함해 전체 파인튜닝.
- steps=100,000, save_freq=5,000 (체크포인트 20개 저장 예정)
- batch_size=64 (GPU당), 이 환경 기준 GPU 4장(RTX A6000 x4) 자동 감지
  -> NUM_GPUS=4, effective batch size = 64*4 = 256
- wandb 로깅: project=robocasa_turnonsinkfaucet_smolvla, entity=DynamicVLA
- 체크포인트 저장 위치: lerobot/outputs/train/202x-xx-xx/xx-xx-xx_smolvla

  AssertionError, 학습 첫 배치부터 죽음: "queried timestamps
  unexpectedly violate the tolerance (0.0001 > tolerance_s=0.0001)".
  원인 분석: mg의 에피소드 100개를 고를 때, 원본 mg의 첫 video 청크
  파일(파일당 최대 ~1942 에피소드)에서 딱 100개만 필요했으므로
  split_dataset이 "부분 재인코딩" 경로(PyAV/SVT-AV1)를 탐 -> 100개
  에피소드(~1236초 분량)를 하나의 새 mp4로 재인코딩하는 과정에서
  프레임 타임스탬프에 아주 미세한(~1e-4초) 누적 drift가 생겨서, 그
  video 파일의 마지막 프레임 근처를 쿼리할 때 기본 tolerance_s=1e-4
  기준을 아슬아슬하게 못 맞춤. (mg 원본 데이터 자체는 정상 -- 에피소드별
  timestamp가 0부터 정상적으로 재시작하는 것 확인함. 문제는 순전히
  재인코딩에서 생기는 부동소수점 drift.)
  -> 1차 수정 시도: train_smolVLA_robocasa.sh에 TOLERANCE_S(기본
     1e-3, 20fps 프레임 간격 0.05초의 2%도 안 돼서 엉뚱한 프레임을
     고를 위험은 없음) 추가하고 --tolerance_s로 전달 -> 그런데도
     똑같은 에러가 재현됨. 원인 추적 결과 **이 프로젝트 자체의 버그**
     발견: src/lerobot/datasets/factory.py의 멀티 데이터셋(브래킷
     [a,b] 문법) 분기가 MultiLeRobotDataset(...)을 만들 때
     tolerances_s를 아예 안 넘겨서, cfg.tolerance_s를 완전히 무시하고
     항상 내부 기본값 dict.fromkeys(repo_ids, 0.0001)로 고정되고
     있었음 (단일 데이터셋 분기는 tolerance_s=cfg.tolerance_s를 이미
     제대로 넘기고 있어서 비대칭적인 버그).
  -> 실제 수정: factory.py의 MultiLeRobotDataset(...) 호출에
     tolerances_s=dict.fromkeys(datasets, cfg.tolerance_s) 추가.
     이후 --tolerance_s=1e-3이 정상 반영되어 문제 해결.

[참고] BATCH_SIZE=64(기본값, scaling.sh와 동일 관례)로는 RTX A6000
  48GB 1장에서 smolVLA 풀 파인튜닝(VLM 포함, freeze_vision_encoder=
  false) 첫 forward에서 바로 CUDA OutOfMemoryError. 이건 버그가
  아니라 하이퍼파라미터 튜닝 필요 사항으로 판단, 스크립트 기본값은
  안 건드리고 검증 실행에서만 BATCH_SIZE=8로 낮춰서 확인함. 실제
  본 학습(3000ep) 돌릴 때는 배치 크기를 낮추거나 gradient
  accumulation 등을 고려해야 함.

11.1 배치 사이즈 이진 탐색
--------------------------------------------------------------------
- 요청: "배치 사이즈 조절을 해서 최대로 돌아가는걸 찾아주고, 그걸 해보고
  그 다음 3000 에피소드로 한 번 돌려서 진짜 돌아가는지 한 번 확인만
  해줘"
- 207ep 테스트 데이터셋으로 이진 탐색 스크립트(probe_batch_size.sh)
  작성해 실행 -> 결과가 "BEST=8"로 나왔는데, 이건 스크립트 버그였음:
  test_batch() 함수 안에서 `echo ... | tee -a "$SUMMARY"`가 stdout에도
  출력되는 바람에, `res=$(test_batch ...)`로 캡처한 값에 여러 줄이
  섞여 들어가서 `[ "$res" == "OK" ]` 비교가 항상 실패 -> 매번 "실패"로
  잘못 판정됨. (실제 로그엔 8/12/20/36 전부 OK로 정상 기록돼 있었음.)
  tee를 파일 전용 리다이렉션(>>)으로 바꿔서 수정 후 low=36(확인된 성공)
  ~ high=64(확인된 OOM) 사이로 재탐색.
- 최종 결과: BATCH_SIZE=48 -> OK (GPU 4장 모두 메모리 48.1~48.5GB
  /49.14GB, 약 99% 사용, 90초간 안정적으로 유지 확인, GPU 사용률
  79~95%). 52, 56은 OOM. 즉 48이 이 데이터셋/설정에서의 실측 최대값.
  마진이 거의 없어(1% 미만 여유) 장시간 학습 중 단발성 OOM 위험은
  있지만, 사용자가 "최대"를 명시적으로 요청했으므로 48을 그대로 채택.

11.2 3000ep(human 107 + mg 2893) 첫 시도에서 새로 발견한 버그
--------------------------------------------------------------------
- 100ep(mg)까지는 문제없었지만, 2893ep로 확장하자
  (dataset_tools.split_dataset 내부) _copy_and_reindex_data 에서
  `ValueError: cannot convert float NaN to integer` 발생.
- 원인 분석(전수 스캔): mg 데이터셋은 v2.1->v3.0 변환 시 여러 개의
  data 파일로 나뉘어 저장되는데(고정 개수가 아니라 파일 크기 기준
  자동 분할, 대략 1942/1943/1931/1937개 에피소드씩 5개 파일), 이
  프로젝트 기존 코드인 convert_dataset_v21_to_v30.py가 **매 파일
  경계마다 그 경계의 첫 에피소드를 이전 파일 소속으로 잘못 기록**하는
  버그가 있었음. 예: 실제로는 file-001의 첫 에피소드인 1942번이
  메타데이터상 file-000 소속으로 잘못 적힘. dataset_tools는 이
  메타데이터(선언값)를 믿고 어느 파일에서 읽을지 결정하기 때문에,
  선택 범위가 파일 경계를 넘는 순간 해당 에피소드의 실제 데이터를
  못 찾아서 빈 dataframe -> NaN.
  전수 검사 결과 정확히 4곳 (1942, 3885, 5816, 7753 -- 파일 경계마다
  하나씩)에서 동일 버그 확인. 우리가 필요한 0~2892 범위엔 1942번이
  걸림.
- 해결: tools/fix_episode_file_index.py 신규 작성. 실제 data/*.parquet
  파일들을 스캔해서 각 episode_index가 물리적으로 어느 chunk/file에
  있는지 파악한 뒤, meta/episodes/*.parquet에 선언된
  data/chunk_index·data/file_index 중 실제와 다른 것만 정정. 데이터
  행/비디오는 전혀 안 건드림, 멱등적(재실행 시 불일치 0개면 아무 것도
  안 함). **사용자 승인 받고** mg 원본(레포 밖)에 즉시 적용 ("수정해서
  다시 확인해줘 다 수정해도 돼").
- convert_robocasa_to_v30.sh의 convert_one()에도 통합: ensure_frame_index.py
  다음 단계로 fix_episode_file_index.py를 항상 실행하도록 추가. 이제
  이 스크립트만 돌리면 mg류 데이터셋의 두 가지 알려진 v3.0 변환
  결함(frame_index 누락, 파일 경계 오프바이원)이 전부 자동으로
  고쳐진 상태로 나옴.

11.3 검증 스크립트의 타임아웃이 너무 짧아서 진행 중이던 빌드를 죽인 실수

12.2 환경이 이전 세션과 달라져 있음을 발견
--------------------------------------------------------------------
- 이 세션의 lerobot-VAI 리포(git 이력·소스 코드, 즉 factory.py의
  tolerances_s 수정, lerobot_dataset.py의 environment_state pop 수정,
  tools/ 밑 스크립트들)는 11절까지의 결과가 전부 그대로 남아 있었음.
- 반면 리포 안의 `dataset_git/`(subset 캐시)과 `lerobot/outputs/train/`,
  tmux 세션 "smolvla" 는 전부 없어져 있었음(컨테이너/세션 재시작으로
  추정) -- 즉 11절에서 tmux에 올려뒀던 3000ep 실전 학습은 이 세션
  기준으로는 더 이상 존재하지 않음. 처음부터 다시 데이터 prep이 필요한
  상태.
- `/root/Desktop/workspace/jiyun/robocasa/datasets`(리포 밖, 별도 마운트)
  는 그대로 유지되어 있었음: TurnOnSinkFaucet human/mg, IIWA, UR5e 등
  5개 데이터셋 전부 codebase_version="v3.0"으로 이미 변환된 상태 그대로
  (9절/10절/11절에서 in-place로 적용한 v2.0->v3.0 변환, frame_index
  추가, mg의 timestamp/next.reward float32 캐스팅까지 전부 보존됨).
  즉 convert_robocasa_to_v30.sh를 다시 돌릴 필요는 없었음.
- nvidia-smi로 GPU 상태 확인: GPU 0-3은 33~46GB가 이미 사용 중(사용률은
  0%로 유휴 상태 -- 아마 다른 프로세스가 점유한 채 idle이거나 orphaned
  메모리, 이 컨테이너의 ps로는 소유 프로세스가 안 보임 -- 다른 세션/
  사용자 작업으로 추정, 손대지 않음). GPU 4-7은 완전히 비어 있어서
  (0MiB, 0%) 사용자가 지정한 "GPU 4,5,6,7만 사용" 요청과 실제로 딱 맞는
  상태였음.

12.3 train_smolVLA_robocasa.sh 1차 검증에서 발견한 버그: wandb 로그인
--------------------------------------------------------------------
- dataset_git가 없어서 데이터 prep부터 다시 실행됨(TOTAL_EPISODES=207
  = human 107 전부 + mg 100, BATCH_SIZE=8, GPU_IDS=4,5,6,7 로 축소
  실행). Prep 자체는 정상 완료.
- 그런데 accelerate launch 진입 후 학습 시작 직전에 크래시:
  `wandb.errors.errors.UsageError: No API key configured. Use
  \`wandb login\` to log in.` 이 환경엔 wandb 로그인이 안 되어 있음
  (~/.netrc 없음, WANDB_API_KEY 없음). GPU 제한과는 무관한, 이
  환경(컨테이너)의 wandb 자격 증명 부재 문제.
- WANDB_MODE=offline 환경변수를 그냥 export 해봤지만 무시됨 -> 원인
  확인: src/lerobot/rl/wandb_utils.py::WandBLogger.__init__ 이
  `mode=self.cfg.wandb.mode if ... else "online"` 로 wandb.init()에
  mode를 명시적으로 넘기고 있어서, 환경변수 WANDB_MODE는 이 명시적
  kwarg에 항상 덮어써짐(코드 자체의 설계 -- 버그는 아님, 다만 CLI로
  이 값을 넘기는 옵션이 두 학습 스크립트 어디에도 없었음).
- 해결: train_smolVLA_robocasa.sh와 (신규) train_smolVLA_robocasa_x.sh
  둘 다에 `WANDB_MODE="${WANDB_MODE:-online}"` 변수를 추가하고
  `--wandb.mode="${WANDB_MODE}"` 를 accelerate launch 커맨드에 추가.
  기본값은 "online"이라 기존 동작(실 GPU 머신에서 wandb 자격증명이
  있는 경우의 정상 로깅)은 그대로 유지되고, 이 검증 환경처럼 자격증명이
  없는 곳에서는 `WANDB_MODE=offline`으로 스모크 테스트만 돌릴 수 있게
  됨(오프라인 로그는 run 출력 디렉토리 밑에 로컬로만 저장, 업로드 없음).

--------------------------------------------------------------------
12.4 train_smolVLA_robocasa.sh 최종 검증 결과 (GPU 4,5,6,7)
--------------------------------------------------------------------
- `TOTAL_EPISODES=207 BATCH_SIZE=8 GPU_IDS=4,5,6,7 WANDB_MODE=offline
  ./train_smolVLA_robocasa.sh` 재실행 (데이터는 이미 prep되어 있어
  스킵) -> accelerate 4-GPU 기동 -> SmolVLM2-500M-Video-Instruct 로드
  -> "Start offline training on a fixed dataset, effective batch size:
  32" -> 267 스텝까지 에러 없이 정상 진행(가속 붙으며 최종 ~2 it/s
  안정화).
- nvidia-smi로 실측: GPU 4,5,6,7만 사용 중(각 ~11.4GB, 사용률
  52~100%), GPU 0-3은 학습 시작 전과 동일하게 변화 없음(건드리지 않음
  확인됨). 즉 "GPU 4,5,6,7만 사용" 요구사항이 실제로 지켜짐을 확인.
- 확인 목적의 스모크 테스트였으므로 SIGKILL로 프로세스 종료(pkill -9 -f
  lerobot_train.py / accelerate launch), GPU 메모리 정상 반환 확인.

12.5 새 데이터 소스 스키마 사전 점검
--------------------------------------------------------------------
- 학습에 새로 추가할 4개 소스(atomic human, atomic mg, IIWA, UR5e)의
  meta/info.json을 전부 비교: action(float64[12]),
  observation.state(float64[16]), timestamp/next.reward(둘 다
  float32[1]), 3개 카메라(video[256,256,3]) 등 모든 feature의
  dtype/shape가 4개 데이터셋 전부 완전히 동일함을 확인 (9절/10절에서
  mg에 적용했던 float32 캐스팅과 frame_index 추가가 이미 영구
  반영되어 있어서, cross-embodiment 데이터를 추가로 합쳐도 새로운
  dtype 불일치가 없음).

12.6 새로 만든 파일
--------------------------------------------------------------------
- tools/prepare_robocasa_x_dataset.py (신규)
    - tools/prepare_robocasa_dataset.py의 build_subset()과 동일한
      로직(단일 소스씩만 다루는 dataset_tools.split_dataset/
      remove_feature 사용, 크로스 데이터셋 병합 없음)을 4개 소스로
      확장:
        - panda_human: 항상 전체 유지 (--source-panda-human)
        - panda_mg: panda_human과 합쳐서 --panda-total-episodes(기본
          1000)가 되도록 앞에서부터 필요한 개수만 (--source-panda-mg)
        - iiwa: 항상 전체 유지 (--source-iiwa)
        - ur5e: 항상 전체 유지 (--source-ur5e)
      각 소스는 --cameras로 지정한 카메라만 남김(기본: 기존 스크립트와
      동일하게 robot0_agentview_right + robot0_eye_in_hand, left 드롭).
      결과는 <output-root>/raw/{panda_human,panda_mg,iiwa,ur5e} 로
      독립적으로 저장(merge 없음, 학습 시 MultiLeRobotDataset의
      브래킷 문법으로 실시간으로만 섞음 -- 9절/10절과 동일한 이유로
      물리적 merge를 피함).
      소스 경로 기본값은 실제 확인된 5개 데이터셋 경로로 하드코딩
      (IIWA/UR5e는 cross_embodiment/lerobot_datasets 아래 유일한
      TurnOnSinkFaucet 태스크 경로; PandaOmron_RethinkGripper/
      PickPlaceSinkToCounter는 사용자가 "IIWA와 UR5e"만 명시했고
      태스크도 다르므로 제외).
      idempotent(이미 원하는 개수로 존재하면 스킵), --force로 재빌드
      가능 -- prepare_robocasa_dataset.py와 동일한 관례.

- train_smolVLA_robocasa_x.sh (신규)
    - train_smolVLA_robocasa.sh와 동일한 구조(데이터 prep 호출 ->
      accelerate multi-GPU launch)를 그대로 따르되, prepare_robocasa_x_
      dataset.py를 호출하고 `--dataset.repo_id=
      "[panda_human,panda_mg,iiwa,ur5e]"` 로 4개 데이터셋을 함께 학습.
    - PANDA_TOTAL_EPISODES(기본 1000), SOURCE_PANDA_HUMAN/
      SOURCE_PANDA_MG/SOURCE_IIWA/SOURCE_UR5E, CAMERAS, DATASET_ROOT
      (기본 dataset_git/robocasa_x), GPU_IDS, BATCH_SIZE 등 전부
      기존 스크립트와 동일한 방식으로 환경변수 오버라이드 가능.
    - wandb project는 별도로 "robocasa_x_smolvla" 사용(기존
      "robocasa_turnonsinkfaucet_smolvla"와 구분).
    - job_name="smolvla_robocasa_x_${PANDA_TOTAL_EPISODES}".

- train_smolVLA_robocasa.sh (수정)
    - WANDB_MODE 변수 + --wandb.mode 플래그만 추가(12.3 참고). 다른
      로직은 변경 없음.

- src/lerobot/datasets/factory.py, src/lerobot/datasets/lerobot_

  dataset.py, tools/ensure_frame_index.py, tools/fix_episode_file_

12.7 train_smolVLA_robocasa_x.sh 최종 검증 결과 (GPU 4,5,6,7)
--------------------------------------------------------------------
- `BATCH_SIZE=8 GPU_IDS=4,5,6,7 WANDB_MODE=offline
  ./train_smolVLA_robocasa_x.sh` 를 기본값(PANDA_TOTAL_EPISODES=1000)
  그대로 실제로 실행.
- 데이터 prep 결과: panda_human=107(그대로 복사, 재인코딩 없음) +
  panda_mg=893(9524개 중 앞쪽 893개, split_dataset 경유 -- 유일하게
  비디오 재인코딩이 필요했던 부분, 데이터 prep 전체 시간의 대부분을
  차지) + iiwa=990(전체, max_episodes=None이라 split 없이 순수 카메라
  드롭 복사만 -> 빠름) + ur5e=997(전체, 마찬가지로 빠름)
  = 총 2,987 에피소드. 107+893=1000 (Panda 목표 정확히 달성).
- 학습 시작 로그에서 `keys set() of {panda_human,panda_mg,iiwa,ur5e}
  were disabled` (전부 빈 집합) 확인 -- 12.5에서 확인한 대로 4개
  데이터셋의 feature 스키마가 완전히 동일해서 MultiLeRobotDataset이
  아무 필드도 걸러내지 않고 전부 사용함을 실측으로도 확인.
- "Start offline training on a fixed dataset, effective batch size:
  32" 이후 252 스텝까지 에러 없이 정상 진행.
- nvidia-smi 실측: GPU 4,5,6,7만 사용(각 ~11.4GB, 사용률 75~86%),
  GPU 0-3 변화 없음.
- 확인 목적이므로 SIGKILL로 종료, GPU 메모리 정상 반환 확인. 데이터는
  dataset_git/robocasa_x/raw/ 에 그대로 남아있어(2,987 에피소드 전체
  이미 준비 완료 상태) 다음에 그냥 ./train_smolVLA_robocasa_x.sh 를
  실행하면 데이터 prep 없이 바로 학습이 시작됨.

12.9 남은 것 / 참고
--------------------------------------------------------------------
- 두 스크립트 모두 "동작 확인"만 했고(짧은 스텝 수, 작은 배치),
  100,000 스텝까지 가는 실전 학습은 아직 아무것도 tmux 등에 올려두지
  않음 -- 필요하면 11.4절과 동일한 방식(tmux new -s ... 안에서
  BATCH_SIZE는 GPU 메모리에 맞게 다시 이진 탐색 필요, GPU_IDS=4,5,6,7
  고정)으로 실제 실행하면 됨. 이번엔 BATCH_SIZE=8만 검증했고 11.1절의
  48(RTX A6000 48GB, human+mg 2대만 학습 기준)은 데이터셋 구성이
  달라졌으니(4개 소스, 2,987 에피소드) 그대로 재사용하지 말고 다시
  탐색 권장.
- GPU 0-3을 점유 중인 프로세스의 정체(다른 세션/사용자 작업으로 추정)
  는 확인하지 않았고 건드리지 않음 -- 필요하면 별도로 확인 요망.
- WANDB_MODE 기본값은 "online"으로 유지했으므로, 실 GPU 머신에서
  wandb 자격증명이 이미 설정돼 있다면(이전 3000ep 실전 학습 때처럼)
  기존과 동일하게 온라인 로깅됨 -- 이번 수정이 실 서비스 동작을 바꾸지
  않음.
- cross_embodiment/lerobot_datasets 안의 PandaOmron_RethinkGripper/
  PickPlaceSinkToCounter(999 에피소드)는 이번 요청에 포함되지 않아
  train_smolVLA_robocasa_x.sh에 넣지 않았음 -- 필요시 같은 패턴으로
  추가 가능.
